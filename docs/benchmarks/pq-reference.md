# v2 混合加密信封引用 · 本地实验记录

2026-11-26 在 Windows 本机用 Chrome 158、两个测试身份和回环中继实测。正文固定为 128 个 ASCII 字节，每组使用独立的混合会话。接收方及时确认时，同向连发 100 条的信封从 209,711 B 降至 70,953 B。对方离线时能省多少，取决于发送方在断线前是否收到了当前发送链的有效回执。

| 消息收发方式 | 原版信封合计 | 引用版信封合计 | 流量变化 |
|---|---:|---:|---:|
| 首条，含握手与适用的回执 | 6,968 B | 7,503 B | +7.68% |
| 及时确认，同向 2 条 | 9,015 B | 8,143 B | −9.67% |
| 及时确认，同向 10 条 | 25,391 B | 13,263 B | −47.76% |
| 及时确认，同向 100 条 | 209,711 B | 70,953 B | −66.17% |
| 两人逐条轮流回复，共 100 条 | 209,621 B | 263,121 B | +25.52% |
| 首个回执丢失，同向 10 条 | 25,391 B | 20,126 B | −20.74% |
| 首次建会话，接收方离线，积压 10 条后一起收取 | 25,391 B | 75,030 B | +195.50% |
| 当前链已确认，接收方离线，再同向积压 10 条 | 20,471 B | 6,401 B | −68.73% |
| 接收方回复一条后离线，发送方在新链上积压 10 条 | 20,470 B | 25,820 B | +26.14% |

表中统计双方实际提交给中继的 `POST /v1/envelopes` 请求体字节，包含计量窗口内的握手、重复封装及所有回执。以同一序号比较，确认后的引用消息从 2,047 B 变为 640 B，每条节省 1,407 B，即 11,256 比特。首封的加密协商字段额外占 248 B，回执占 287 B。轮流回复的测试里每轮都更换发送链，触发新的封装与回执。

三组离线测试均在 Chromium 断开接收方网络并验证其无法访问中继后开始积压。收发双方恢复通信后逐条核对了十条正文，并验证启用引用的会话随后能发出和解开第十一条引用。统计仅涵盖积压的十条及其回执。首次联系时发送方重复携带公开握手和完整封装。回复换链后只重复封装。已确认的同一条链则只需十个引用，重连后额外回执为零。

非空收件箱响应单独计量。同向 100 条从 244,724 B 降至 106,306 B。合并表中上行和这部分下行，双方合计从 454,435 B 降至 177,259 B，减少 61.0%。统计范围排除了目录和预密钥请求、空轮询、HTTP 头及传输层开销。[原始测量数据与每种信封的字节分布](pq-reference-wire.json)

## 从聊天界面发送的流量

同一条链确认后，用浏览器聊天表单逐条发送 10 次，接收方重连后统一收取。记录这一段内两个客户端与中继交换的所有 HTTP 请求体和响应体，包含两次收件箱查询。两组均有一个好友设备，均在发送前完成注册和首次会话。HTTP 头、TCP/IP 帧和空闲时的后台轮询不在计量窗口内。

| 计量窗口内的应用层字节 | 完整封装 | 引用 |
|---|---:|---:|
| 查询好友设备目录，10 次 | 161,450 B | 161,590 B |
| 向中继提交信封，10 次，含中继响应 | 22,491 B | 8,421 B |
| 接收方及发送方各查收件箱一次 | 23,398 B | 9,328 B |
| **合计** | **207,339 B** | **179,339 B** |

信封请求体缩小 68.73%，聊天操作的应用层总量减少 **28,000 B（13.50%）**。界面每发一条消息就重新获取好友设备目录，响应携带设备公钥及预密钥池。引用组的十次目录查询合计占总量约 90%。[各 API 的请求数与字节数](pq-reference-wire.json)

后续已在相同的聊天表单负载上实测[本地好友设备目录缓存](directory-cache.md)，同时计入了 HTTP 头和版本校验。

## 丢包、恢复与安全验证

- 首个数据包在中继接受后丢失，下一条完整消息仍可建立会话。首个回执丢失后，发送端继续发完整封装，收到下一次有效回执才切换引用。永久丢失的正文仍需重发。
- 乱序引用、跨换链迟到的旧消息以及两端重载均通过。新增边界用例验证了当缓存为空时，先到的引用若跨过 41 条，接收端会拒收，持久化状态保持不变。跨过 40 条可成功解密。从保存的会话重启后，重新交付被拒消息及全部 40 条迟到消息，均成功解密。重复交付仍被拒绝。
- 冷重启测试先让一封引用消息留在 SQLite 队列，再关闭浏览器和中继进程。重新启动两个进程后，接收方成功解密积压的引用和之后的新消息。中继默认的内存队列在重启时会清空。
- 每条发送链使用独立回执密钥，通过已加密的完整消息传递。接收方验证消息并成功写入本地会话后，才发出 HMAC-SHA-256 回执。回执绑定两端设备地址、发送链 DH 公钥及完整 ML-KEM 密文的 SHA-256 摘要。引用消息还通过 AES-GCM 验证这些关联信息。换链仍使用新的 ML-KEM 封装。
- 未知引用、跨链或错误设备回执、篡改、重放、缺失或同时携带两种封装字段的测试均按预期拒绝。被拒绝的数据不会推进已保存的棘轮。模拟接收端存储写满时没有发出回执，恢复存储后下一封完整消息可建立会话。新旧能力混用时仍可使用完整信封。
- 恢复测试以保留设备身份和会话存储为前提。接收方在确认后清除或回滚本机缓存，旧引用可能无法解密。现有身份指纹核验和浏览器密钥存储的信任条件仍然适用。这次验证覆盖上述行为，尚未进行独立的密码学安全审计。

## 保存点与复跑

本地试验通过回环中继启用。两端均使用 `?pqrefs=0` 并注册新的测试身份，可复现原版基线。本地 Windows 包位于 `dist/ECNUchat-v2-Windows.zip`。首次保存时 Node 用例 22 项通过，Python 用例 87 项通过、14 项跳过。续跑时核验了 9 项引用协议测试和 5 项浏览器及进程重启测试，全部通过。

