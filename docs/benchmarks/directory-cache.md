# 好友设备目录缓存的本地流量实测

2026-11-26 在 Windows 和 Chrome 158 上，从聊天表单发送十条 128 字节正文。双方均使用已经确认的混合加密发送链。分别运行旧的逐条查询和新的本地缓存，两组的接收方重连后都正确解密了十条消息。计入请求头、响应头和实际发生的预检后，最终复跑节省 **169,069 B（84.86%）**。

| 十次发送，加上重连后的两次收件箱查询 | 每条查完整目录 | 本地缓存 |
|---|---:|---:|
| 中继 HTTP 请求次数 | 22 | 12 |
| 单独的目录查询 | 10 | 0 |
| 双方与中继交换的请求体和响应体 | 179,339 B | 17,838 B |
| 双方与中继交换的 HTTP/1.1 总字节 | 199,235 B | 30,166 B |

两组均使用隔离的浏览器身份和回环中继。接收方离线期间，发送方在聊天表单逐条发送。接收方重连后查询一次收件箱，发送方也查询一次。测量读取中继的实际 HTTP 字节流，包含查询串、请求行、状态行、HTTP 头、CORS 预检和正文。注册、网页静态资源及 TCP/IP 链路开销在统计范围之外。自动轮询在基准实验中关闭，收件时机由程序控制。HTTP 大小可能随浏览器和预检缓存变化。

从添加好友、首次发送到收到首个 PQ 回执另行计量，冷启动从 133,218 B 降至 96,994 B。其中第一次读取紧凑目录用去 1,170 B HTTP 流量。建立会话仍要获取一次性预密钥，接收方仍会读取并验证发送方的公钥材料。前一轮十条消息的 HTTP 总量分别为 199,279 B 和 30,190 B，两轮的正文总量一致。[按阶段和接口分项的原始数据](directory-cache-wire.json)

## 设备变化与安全边界

- 缓存按中继、当前账号、设备及本机身份指纹隔离。每次使用缓存投递时，中继在入队的同一把锁内核对好友目录版本。设备变化会触发冲突，客户端重新拉取紧凑目录。多设备发送只补发给此次尚未成功投递的已验证设备。未知网络错误不会触发自动重发。
- 当前打开的聊天随收件箱轮询获取目录版本，默认间隔 5 秒。这会向本机中继提供当前选中的好友用户名。其他聊天在下次使用缓存发送时也会核对版本。断网或浏览器暂停轮询期间，显示的目录可能滞后。
- 已撤销设备无法接收后续投递，中继会丢弃该设备尚未领取的队列。新设备或更换签名身份的设备会显示为待验证。用户通过可信渠道取得该设备的邀请并重新粘贴，客户端核对签名公钥指纹后才允许发送。目录版本只描述中继当前记录，不能代替对方的身份证明，也无法撤回已经交付的密文。
- 缓存保存设备 ID、指纹、能力标记和版本。新的加密会话仍走签名预密钥验证及一次性预密钥消费流程。旧混合会话迁移或目录版本变化后，首次续用时检查当前签名身份和长期密钥。如果签名身份保留、长期 PQ 密钥已更换，客户端重新建立混合会话。若曾经支持混合加密的同一身份缺少签名 PQ 密钥，客户端会停止投递。
- 安全测试使用本机开发中继，覆盖重启复用缓存、增删设备、同一设备名更换身份、发送中撤销、目录刷新失败和指纹不匹配。开发中继允许本地调用注册和撤销接口。测试没有改变中继本身的管理权限，也未做独立密码学审计。

.\.venv\Scripts\python.exe -m v2.tests.benchmark_directory_cache --output docs/benchmarks/directory-cache-wire.json
