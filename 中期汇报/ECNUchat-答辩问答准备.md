## 零、创新性速答（老师必问，先背这一段）

**问：你们这个项目创新点到底在哪？**

**先说人话：** 我们没有发明新的加密算法。创新在于：把 2024–2025 年几篇论文指出的"现行方案还不够"的地方，在一个能跑的完整系统里逐条补上，而且补的每一处都能用测试和攻击演示验证。

**30 秒标准答：** 四点。第一，**后量子做成双层**：Signal 现行部署的 PQXDH 只保护握手，我们连双棘轮的每条新发送链都混入新鲜 ML-KEM 封装（pq-dr-v1），还优先用一次性 PQOPK 并在客户端拒绝降级。第二，**群聊不用 Sender Keys**：逐人双棘轮信封换回逐对前向安全与破密恢复，外加签名哈希链让成员名单可被客户端独立验证——这是对 EuroS&P 2018 批评的直接回应。第三，**初始消息签名覆盖经典与后量子全部握手材料**，且身份公钥首次取得后本地钉住。第四，**实现层加固**：解密原子提交、一次性私钥延迟到首条密文认证成功后才删，堵住伪造包烧钥匙。定位：不发明新原语，创新在把 2024–2025 的论文结论落成一套互相咬合、且通过跨实现互操作（v2 JS ↔ v1，12/12）验证的完整系统。

## 一、专业名词直白解释速查表

> 老师的问题里出现任何下面的词，先在心里把它翻译成人话，再回答。左边是术语，中间是"一句人话"，右边是"在本项目里具体指什么"。

| 术语 | 一句人话 | 在本项目里 |
|---|---|---|
| 端到端加密（E2EE） | 消息只在你和对方的设备上是明文，中间谁都看不懂 | 服务器只转发密文信封，正文、文件、语音都不解密 |
| 对称加密 | 同一把钥匙既上锁又开锁，快，但钥匙怎么安全送到对方手里是个问题 | AES-256-GCM 加密每条消息正文 |
| 非对称加密 | 一对钥匙：公钥谁都能拿，私钥只有自己有 | X25519 做协商、Ed25519 做签名 |
| 公钥 / 私钥 | 公钥像"挂锁"，可以随便发给别人；私钥像"钥匙"，只能自己留着 | 公钥放服务器目录里公开，私钥锁在本地保险库 |
| DH / ECDH 密钥协商 | 两个人各出一个秘密，当众交换"半成品"，各自算出同一把钥匙，全程没人传过钥匙本身 | X25519 就是 ECDH 的一种实现；握手做 4 次 DH |
| X25519 | 一种具体的 DH 协商算法（用 Curve25519 曲线），快、成熟、字节格式有国际标准 RFC 7748 | 所有经典协商都用它：身份钥、SPK、OPK、临时钥、棘轮钥 |
| 数字签名 | 相当于本人的印章：盖了章的文件，别人能验"确实是你盖的、内容没被改过"，但伪造不了 | Ed25519 签名：签 SPK、签初始消息、签群状态 |
| Ed25519 | 一种具体的签名算法，和 X25519 同出 Curve25519 家族 | IK_sign 用它；和协商钥 IK_dh 是分开的两把钥 |
| 哈希（Hash） | 给任意数据算一个固定长度的"指纹"：内容改一个字，指纹全变；且没法从指纹反推原文 | SHA-256：算指纹、算群状态哈希、混进 HKDF |
| HMAC | 带钥匙的哈希：只有拿着钥匙的人能算出正确的"指纹"，用来防篡改、也用来推钥匙 | 对称棘轮用 HMAC(CK, 0x01) 推消息钥、HMAC(CK, 0x02) 推下一把链钥 |
| KDF / HKDF | "钥匙加工厂"：把一堆原始秘密材料搅匀、拉长，切成不同用途的钥匙 | HKDF-SHA256：握手出 SK（info=x3dh-v1 / pqxdh-v1）、棘轮换链出新根钥（dr-v1 / pq-dr-v1） |
| 域分离（info 标签） | 给每个用途的钥匙贴不同标签，保证同一批材料在不同场合切出的钥匙互不串用 | x3dh-v1、pqxdh-v1、dr-v1、pq-dr-v1 四个标签互不相同，防跨协议攻击 |
| 预密钥（PreKey） | 提前放在服务器上的"一次性或中期钥匙"，让对方在你不在线时也能先把会话建起来 | SPK（中期，签过名）+ OPK（一次性，20 把）+ PQOPK（后量子一次性，8 把） |
| 公钥包（bundle） | 对方全部公钥打包成一份"名片"：身份钥 + 预密钥，放在服务器上供人取用 | 取用前先验 SPK 签名；身份公钥首次取得后本地钉住 |
| 握手（Handshake） | 聊天开始前，双方先协商出会话钥匙的那套开场动作 | X3DH + PQXDH：四次 DH + 一次 KEM 封装 → SK |
| SK（会话密钥） | 握手算出的"总种子"，是棘轮的起点，本身不加密任何消息 | 只喂给双棘轮当根钥种子 |
| RK（根钥） | 棘轮的"总账本钥匙"，每次换链时更新，负责生出新链钥 | 保存在棘轮状态里，随 DH 棘轮滚动 |
| CK（链钥） | 一条发送/接收链的当前钥匙，用一次就向前滚一格 | 对称棘轮的核心状态 |
| MK（消息钥） | 真正加密一条消息的那把钥匙，一条消息一把，用完立刻删除 | 由 CK 经 HMAC 0x01 现推现用 |
| 棘轮（Ratchet） | 像只能往前转的齿轮：钥匙只能向前演进，转过去就回不来 | 双棘轮 = DH 棘轮（换链）+ 对称棘轮（逐条滚） |
| 前向安全（Forward Secrecy） | 今天钥匙泄露，也解不开昨天的消息 | 因为每条 MK 用完即删、HMAC 单向倒推不回 |
| 破密恢复 / 后向保密（PCS） | 钥匙泄露之后，双方再正常聊几句，安全性自己"长回来" | 对方回复、双方换过新棘轮公钥之后成立；不是泄露瞬间 |
| AEAD / AES-256-GCM | 一种"加密 + 防篡改"打包好的算法：密文被改一个字节，解密直接报错 | 每条消息、文件分片、语音帧、保险库都用它 |
| nonce | 配合钥匙使用的"一次性随机数"，同一把钥下绝不能重复 | 每条消息一把新 MK，所以随机 nonce 偶尔撞了也落在不同钥上；文件分片用"随机前缀+块序号"保证不重复 |
| AAD（附加认证数据） | 不加密、但一起"封印"的数据：改了它，解密同样报错 | 把发送方、接收方、序号、棘轮公钥绑进每条消息的 GCM 标签 |
| 中间人攻击（MITM） | 攻击者插在两人中间，两边都以为在和对方说话，其实都在和攻击者说话 | 本项目的头号威胁：服务器换公钥包就是这种攻击 |
| 重放攻击 | 把一条旧密文原样再发一遍，骗接收方当新消息处理 | 已处理的 (棘轮公钥, 序号) 再次出现直接拒绝 |
| 降级攻击 | 骗双方"退回"到更弱的模式（比如把后量子部分剥掉，只剩经典加密） | 双方都支持 PQ 时，缺 KEM 的握手/新链直接拒绝，不静默退回 |
| 威胁模型 | 先假定"敌人能干什么"，再在这个假定下谈安全——不设假定的"安全"是空话 | 假定：服务器可作恶、网络可窃听篡改重放、终端可能被短时攻破 |
| 元数据 | 不是消息内容，而是"谁在什么时候给谁发了多大的消息"这类外围信息 | 本项目未保护（无密封发送者），是已知缺口 |
| 密封发送者（Sealed Sender） | 连"谁发的"都对服务器保密，服务器只知道收件人 | 没做，列在后续计划 |
| 头加密（Header Encryption） | 把消息头（序号、棘轮公钥等）也加密，少给观察者线索 | 没做，已知缺口 |
| 后量子密码（PQC） | 设计成"量子计算机也解不开"的新一代公钥算法 | ML-KEM-768（基于格难题），已标准化，不是实验品 |
| KEM（密钥封装机制） | 后量子版的"协商"：一方把秘密装进只能由对方私钥打开的"保险箱"（封装），对方拆开（解封装）得到同一个秘密 | encaps 产生共享秘密 + 密文 ct；decaps 用私钥还原共享秘密 |
| ML-KEM-768 | 标准化后的 KEM（前身是 Kyber），768 是安全等级档位（约 NIST 第 3 级） | PQK / PQOPK 用它；答辩时务必说清"不是 Kyber" |
| 混合握手（Hybrid） | 经典和后量子两套一起上：安全性取两者之强，任破一套还有另一套 | PQXDH = X3DH 四次 DH + ML-KEM 封装，一起喂 HKDF |
| 先存后解（Harvest Now, Decrypt Later） | 对手今天先把密文存下来，等将来有了量子计算机再解——所以后量子要现在就上 | 这是做 PQXDH 和混合棘轮的直接动机 |
| Sender Keys | Signal 群聊方案：一把群发钥匙分发给所有人，正文走发送者的对称链，快但逐对安全性弱 | 我们**不用**它，改用逐人信封（见 Q13、Q19） |
| MLS | 新一代群聊协议标准（RFC 9420），为大群设计，有正式的群钥匙演进 | 我们没用：课程规模下逐人信封更能保留逐对性质；大群生产环境应考虑它 |
| 哈希链（Hash Chain） | 每一环都包含上一环的指纹：改历史任何一环，后面全对不上 | 群成员状态链：每纪元带前驱哈希 + 成员签名 |
| 纪元（Epoch） | 群状态的"版本号"：每变一次成员，纪元 +1 | 本项目规则：每纪元只增一人 |
| 指纹 / 安全码 | 把对方身份公钥算成一串短编码（这里是 16 组十六进制），两人线下对一对，对上就证明没被换包 | 指纹 = SHA-256(IK_sign 公钥）；核对后本地钉住 |
| 本地钉住（Pinning） | 第一次见到的身份公钥就记死，以后再变就报警拒绝——把攻击窗口压到"第一次接触之前" | 客户端对 IK_sign / IK_dh 都做 |
| 挑战应答（登录） | 服务器出一道"用私钥签个名"的题，能签对就证明你持有私钥，不用把口令给服务器 | 本项目登录方式：服务器不存口令 |
| PBKDF2 / 盐 | 把人口令"慢火熬"成钥匙：故意迭代很多次让猜口令变贵；盐是随机数，保证两人口令相同也熬出不同钥匙 | 600,000 次迭代 + 16 字节随机盐 → 32 字节保险库钥 |
| 跳过缓存（Skipped-Key Cache） | 消息乱序到达时，先把中间序号的消息钥算出来存着，等那条消息到了直接用 | 上限 40 把：防攻击者用巨大序号逼你算几万把钥匙 |
| 原子提交（Atomic Commit） | 解密先在副本上试，全部成功才把状态正式更新；失败就当无事发生 | 防伪造包"烧掉"合法消息的钥匙（见 Q10） |
| 互操作（Interop） | 两个独立写出来的实现能互相通话、字节级对齐——证明实现的是"协议"，不是自说自话 | v2 的 JS 实现 ↔ v1 Python 引擎，后量子互操作 12/12 |
| UC 证明 / 构造对齐 | UC 是最强的一类形式化安全证明框架；"构造对齐"指我们的拼装方式和被证明过的构造一致，但没在本仓库重跑证明 | 答辩立场：构造对齐 ≠ 已证明（见 Q11） |

## 二、算法类

### Q1：X3DH 为什么要做四次 DH？少一次行不行？
**先说人话：** 四次 DH 就像四道独立的锁，每道锁防一种具体的坏事。老师问这个，是想看你是不是真懂每一道锁在防什么，而不是背了一个"四次"的数字。
**标准回答：** 四次各管一件事。DH1 把发起方的长期身份绑到接收方**签过名**的 SPK 上，防止服务器塞无背书的预密钥；DH2 把本次临时钥绑到对方长期身份，保证这次会话是给「这个人」的；DH3 让临时钥再和 SPK 算一次，这样长期身份钥将来泄露，没有当时的临时私钥也重算不出这次的 SK 材料；DH4 用掉一把一次性预密钥，给这次握手加一次性。去掉 DH1，目录攻击（服务器换 SPK）就没有密码学阻拦；去掉 DH3，长期钥泄露后历史会话的握手材料可被重算。
**可能追问：** 「这正是 Cohn-Gordon 等 EuroS&P 2017 阶段树分析里的绑定结构，我们按规范实现，`src/x3dh.py` 里四次 DH 一一对应。」若问"DH 到底怎么算出同一把钥"：双方各用自己的私钥和对方的公钥做 X25519，数学性质保证 A 的私钥配 B 的公钥、B 的私钥配 A 的公钥，结果字节完全相同，全程没传过这把钥本身。

### Q2：没有一次性预密钥（OPK）时还安全吗？
**先说人话：** OPK 是"锦上添花"的一层，不是地基。没有它握手照样成立，只是少了一次性。
**标准回答：** 仍然安全，只是少了 DH4 那一层一次性。SK 由 DH1‖DH2‖DH3 过 HKDF 得到，双方照样一致——单测同时覆盖有 OPK 和无 OPK 两条路径。OPK 的作用是「用完即删」：它对应的私钥在首条密文认证成功后立即删除，使这次握手的材料更难被事后拼凑。工程上池子 20 把、少于 5 把自动补满，所以无 OPK 只是兜底情形。
**可能追问：** 问"为什么删除要等首条密文认证成功"：防伪造包烧钥匙——若一收到假的初始消息就删私钥，攻击者发假包就能把 OPK 一把把烧光（见创新点四）。问"OPK 用完新会话怎么办"：池子自动补满到 20，补满前的会话走无 OPK 路径，安全性如上。

### Q3：为什么 SK 不直接拿来加密消息？用一把 ECDH 密钥加密全部消息不行吗？
**先说人话：** 一把钥用到底，等于"钥匙丢一次，全部历史陪葬"。SK 的角色是种子，不是钥匙本体。
**标准回答：** 不行，那样没有任何前向安全：SK 一旦泄露，历史和未来全部消息一起完。我们的 SK 只做双棘轮的根钥种子，真正的消息钥是每条消息现推的 MK，用完即删。题目三句话的对应关系也在这里——ECDH 负责「协商出起点」，不是「一把钥用到底」。
**可能追问：** 问"种子和钥匙有什么区别"：SK 经过 HKDF 展开成根钥 RK，再经棘轮不断演进出 CK、MK——每一步都是单向的，从后面的钥匙反推不回 SK 和更早的 MK。问"微信那种一把会话钥有什么问题"：见 Q26，传输层加密的会话钥在服务器手里，性质完全不同。

### Q4：前向安全和破密恢复（PCS）到底在哪个时间点成立？请说准确。
**先说人话：** 这是老师最爱抠精度的一题。前向安全看"单条消息的钥匙删没删"，破密恢复看"双方换没换新棘轮钥"——两个时间点都不是"泄露的那一刻"。
**标准回答：** 前向安全的时间点是「这条消息的 MK 已经用完并删除」：之后链钥再泄露，HMAC 单向，倒推不回 MK。破密恢复**不是**泄露后立刻成立：准确时间点是「对方刚回复、双方都换过新的棘轮公钥之后」——新 DH 输出混入根钥，旧链钥推不出新链。对方还没回复之前，发送方仍在旧链上，那一段只有前向安全、没有恢复。
**可能追问：** 「这个时间点采用 CSF 2016（Cohn-Gordon 等）对 post-compromise security 的定义，我们在报告里也是这样写的。」若问"泄露期间对方一直不回复会怎样"：那段窗口内新发的消息没有 PCS 保护，只有前向安全——这是双棘轮的固有性质，不是实现缺陷，Signal 同样如此。

### Q5：AES-GCM 的 nonce 如果重复会怎样？你们怎么保证不重复？
**先说人话：** GCM 有个著名死穴：同一把钥下 nonce 用两次，等于把防篡改的钥匙送人。我们的解法不是"小心翼翼管 nonce"，而是"每条消息换一把新钥"，从根上绕开。
**标准回答：** GCM 在同一把钥下 nonce 重复是灾难性的（可恢复认证钥并伪造）。我们每条消息一把**全新的 MK**（对称棘轮推出、用完即删），所以即使 12 字节随机 nonce 偶然重复，也是落在不同钥上，不构成 GCM 的 nonce 复用问题。文件分片那边不同：一把文件钥加密多块，所以 nonce 用「8 字节随机前缀 + 4 字节块序号」构造，块序号保证同钥下不重复，AAD 再绑文件编号、块序号和总块数，块不能对调。
**可能追问：** 问"为什么不用计数器 nonce"：消息层每钥只用一次，随机 nonce 足够且无状态同步问题；文件层恰恰用了序号，就是计数器思想。若问 GCM 标签多少位：128 位，AAD 绑收发双方、序号、棘轮公钥（见讲稿第 10 页）。

### Q6：为什么签名用 Ed25519、协商用 X25519，两把钥分开？Signal 不是一把钥吗？
**先说人话：** 一把钥干两件事，就像"门钥匙兼保险箱钥匙"——丢一次两处全开。我们宁可多带一把钥，换职责清楚。
**标准回答：** Signal 用 XEdDSA 把一把 Curve25519 钥同时用于 DH 和签名。我们故意不做：签名钥和协商钥从生成起就是两把（IK_sign 是 Ed25519，IK_dh 是 X25519）。好处是职责与泄露面分离、实现上不用碰 XEdDSA 的转换细节，每把钥的用途在代码里一眼可指。代价是 bundle 里多一把公钥，对课程项目可接受。
**可能追问：** 问"分开会不会影响指纹核对"：不会，指纹只取 IK_sign 公钥的 SHA-256；IK_dh 随 bundle 一起被钉住。若问"XEdDSA 有什么不好"：不是不好，是转换细节容易实现错，且一把钥两用在安全分析时要额外处理跨用途交互，我们选择更简单的结构。

### Q7：后量子为什么用「混合」？直接全换成 ML-KEM 不行吗？
**先说人话：** 混合 = 双保险。新算法万一将来被发现有经典弱点，还有 X25519 兜底；老算法被量子破了，还有 ML-KEM 兜底。安全性取两者里更强的那个。
**标准回答：** 两个理由。一是稳健：混合后安全性取两者之强——X25519 被量子打破时有 ML-KEM 兜底，ML-KEM 若将来被发现经典攻击面，还有 X25519。二是这正是 PQXDH（Fiedler & Günther, PKC 2025）分析的构造，Signal 的部署也是混合。我们用的是标准化后的 **ML-KEM-768**，不是 Kyber——答辩时这个区别要说清。
**可能追问：** 「HKDF 的输入里还混入了封装公钥的 SHA-256，一次性封装钥和长期钥不能互换冒充。」若问"为什么不用 512 或 1024"：见 Q28。若问"量子计算机还没造出来，为什么现在做"：先存后解——对手今天就能把密文存下来（见 Q27）。

### Q8：服务器扣留一次性后量子钥（PQOPK）怎么办？长期 PQK 泄露又怎么办？
**先说人话：** 扣留只能让这次握手"降一档"，降不到"没有"——因为缺 KEM 的握手会被直接拒绝，对方想把后量子整段剥掉是不可能的。泄露长期 PQK 影响的是"之后"的新链，"之前"用过一次性钥的握手仍然安全。
**标准回答：** 扣留只能让这次握手退到签过名的长期 PQK，KEM 本身拿不掉——因为双方都支持 PQ 时，缺 KEM 的经典握手会被直接拒绝，不存在静默降级；终端 `/pq status` 会显示这次用的是 pqopk 还是 pqk，用户可见。长期 PQK 若日后泄露：用过一次性 PQOPK 且私钥已删的那次握手，SK 仍然算不出来；但泄露之后新开的棘轮链会退回经典 DH 的保障水平——这是我们在报告里明写的边界。
**可能追问：** 问"用户看到 /pq status 显示 pqk 该怎么办"：这只说明本次没拿到一次性钥，不等于被攻击；但如果长期如此，值得警惕服务器在扣留。若问"为什么不把 PQOPK 泄露也防住"：长期钥的定位就是兜底，它泄露后靠经典 DH 继续提供当下安全性、靠一次性钥保住历史——分工如此。

### Q9：为什么握手加了后量子还不够，还要做混合棘轮？
**先说人话：** 只给"开场"上保险，对手就改盯"正片"：握手密文解不开，就囤棘轮阶段的密文，将来逐条链去破。所以每条新链都要再上一次后量子。
**标准回答：** 因为对手的目标会平移：握手密文解不开，就改存棘轮阶段的密文，将来打破每条链的 DH。所以每开一条新发送链，除了 DH 输出，再对对方长期 PQK 做一次新鲜 ML-KEM 封装一起派生（标签 pq-dr-v1）。双方都记录了对方 PQK 后，新链缺封装密文直接拒绝，防止中间人把封装剥掉、把棘轮降级回经典。
**可能追问：** 问"这是 Signal 做的吗"：不是——Signal 现行部署只有握手层 PQXDH，棘轮层仍是经典 DH；这正是我们创新点一"双层"的含义。问"每条链一次封装，性能贵吗"：见 Q29，封装只在换链时发生，不是每条消息。

### Q10：跳过缓存上限为什么是 40？重放怎么防？
**先说人话：** 乱序是网络常态，得允许"先到后面的消息"；但缓存不能无限大，不然攻击者报一个天文数字序号，就能逼你的客户端算钥匙算到死。40 是"够用的乱序深度"和"算力上限"之间的工程取舍。
**标准回答：** 乱序到达时把中间序号的 MK 先算出来缓存，上限必须有：否则攻击者发一个巨大序号，就能逼客户端算几万把钥匙（资源耗尽）。40 是覆盖正常网络乱序深度的工程取值，超限拒绝。重放靠状态：已成功处理的 (dh_pub, n) 再出现直接拒绝，不再走 GCM 试解；且解密先在状态副本上试算、GCM 成功才提交，伪造包不会把合法消息的钥匙提前烧掉。
**可能追问：** 「Alwen 等 EUROCRYPT 2019 把这叫『立即解密』；论文里对多项式大小空隙都成立，我们取 40 是实现取舍，报告里声明了。」若问"40 够吗，微信乱序能到多少"：聊天场景乱序深度通常个位数；40 是留足余量的取值，且超限只是拒绝该条、不影响会话。若问"原子提交失败一次会怎样"：状态完全不变，合法消息随后到达仍可正常解——这正是原子提交的意义。

## 三、论文类

### Q11：你们的安全性是自己证明的吗？这些论文的定理能直接套到你们实现上吗？
**先说人话：** 这题千万别吹。诚实答案是：我们站的是"巨人的肩膀"——拼装方式和被严格证明过的构造一致，但我们没有在自己的代码上重跑一遍形式化证明。老师问这个，恰恰是想听你把这条线划清楚。
**标准回答：** 不能这样声称。我们的立场是「构造对齐」：双棘轮的 kdf_ck、kdf_rk、立即解密、消息钥用后即弃这四块积木与 Bienstock 等 CRYPTO 2022 分析的 F_DR 构造一致；X3DH+双棘轮的整体依据是 Cohn-Gordon 等 EuroS&P 2017 的阶段树证明。但我们没有在本仓库上重跑 UC 证明，也没在证明器里建模——报告第 9 节把「满足/不满足」逐条列了，这是我们写报告时刻意分开的。
**可能追问：** 问"那你们凭什么说自己安全"：三层证据——构造对齐已证明的构造、95 个协议性质与攻击回归测试、两个独立实现的互操作（Q22）。问"UC 是什么"：通用可组合安全框架，能保证协议放进任何大系统里组合使用仍安全，是最强的一类证明标准；我们达不到，也不声称达到。

### Q12：Bienstock 等指出的那个窗口是什么？你们为什么不做 Triple Ratchet？
**先说人话：** 这是论文作者在双棘轮里找到的一个"小窗口"：发送方的棘轮私钥必须留一段时间，这段时间里状态被连偷两次，就能拼出本轮已发的消息钥。我们知道它在，没修，写在缺口里——答辩时主动说，比被问出来强。
**标准回答：** 窗口在发送棘轮私钥 dhs_priv：它必须留到对方下一把棘轮公钥到来，这段时间里若同一方的状态被连续取走两次，可以拼出本轮已经发出的消息钥匙。补法是他们的 Triple Ratchet（F_TR），在算出本轮 DH 后再对私钥材料做一次本地单向更新。我们没实现，所以这个窗口还在——它已列入已知缺口和后续计划（先评估再实现），答辩时主动承认比被问出来好。
**可能追问：** 问"窗口有多严重"：需要攻击者在同一轮内连续两次拿到同一方完整状态，是很强的攻击者假设；且只影响本轮已发消息，不影响历史（前向安全仍在）。问"为什么不顺手做了"：Triple Ratchet 改变棘轮核心状态机，要重新做性质测试与互操作验证，超出中期范围；先评估再实现写在计划里。

### Q13：More is Less 具体批评了什么？你们的群方案就全解决了？
**先说人话：** 这篇论文等于给 Signal 群聊写了份"差评"：一把群钥分发下去之后，正文和成员名单都失去端到端保护。我们逐条回应了这两点——但别说"全解决"，我们自己还留了两条尾巴，主动交代。
**标准回答：** 它批评两点：一是 Sender Keys 让群正文走发送者的对称链，没有 DH 棘轮，future secrecy 在分发钥匙那一刻断裂；二是群成员管理没有端到端保护，服务器说了算。我们逐人信封回应第一点（每封保留两人会话的前向安全与破密恢复），签名哈希链群状态回应第二点（伪造名单、幽灵成员、名单分歧都会被客户端拒绝或由哈希链断裂暴露）。没解决的也有：入群「同意」记在服务器的邀请表上、不在签名里，恶意服务器可以谎称对方已同意；另外没有群签名。这两条报告里都写了。
**可能追问：** 问"为什么不用 MLS 一步到位"：MLS 是为成百上千人大群设计的完整协议，复杂度远超课程项目；8 人小群里逐人信封用线性成本换回逐对性质，是自觉的取舍（与 Q19 是同一个取舍）。问"幽灵成员是什么"：服务器偷偷往群里塞一个成员收信封，正文就多一份泄露——哈希链让名单的每一次变化都必须有现成员签名，塞不进来。

### Q14：为什么 HKDF 的盐用 32 个零字节、info 用 x3dh-v1 这种字符串？
**先说人话：** 盐全零不是偷懒——当输入材料本身熵足够高时，HKDF 的安全性不靠盐的随机性。info 字符串则是"用途标签"：贴了标签，同一批材料在不同用途里切出的钥匙永远不会撞车。
**标准回答：** 这是 Signal 规范与 HKDF（Krawczyk 2010）extract-then-expand 的用法：盐为全零时 HKDF 退化为以 HMAC 为核心的提取，安全性由输入密钥材料的高熵保证（四次 DH 输出拼接）。info 是域分离标签：x3dh-v1、pqxdh-v1、dr-v1、pq-dr-v1 互不相同，保证同一份材料在不同用途、不同版本、经典与后量子路径之间不会串用——这是防跨协议攻击的标准做法。
**可能追问：** 问"跨协议攻击是什么"：同一把钥匙被两个协议共用，攻击者把协议 A 的消息搬到协议 B 里骗过验证；域分离让两边算出的钥匙天然不同，搬过去也解不开。问"v1 是版本号？改了怎么办"：对，标签带版本就是为了将来升级算法时新旧钥匙自动隔离。

### Q15：Bellare–Tackmann 的 GCM 多用户安全和你们有什么关系？
**先说人话：** 这篇论文讨论的是"一把钥用很多次会慢慢变弱"，而我们的用法是"一把钥只用一次"，所以它对我们是参数参照，不是直接定理——老师问这个是看你会不会乱套文献。
**标准回答：** 他们讨论的是「一把长期 GCM 钥加密很多记录」时安全界如何随用户数退化。我们每条消息一把新 MK、用完即弃，天然避开了长期钥多记录的退化情形，所以不把那条 TLS 语境的定理当成聊天本身的定理引用——它在我们的文献表里是参数层面的参照，报告里也是这样定位的。
**可能追问：** 问"那你们 GCM 的安全依据是什么"：GCM 本身的 AEAD 安全性（原语论文）+ 每钥单消息的使用方式（Q5）；文件层同钥多块，靠构造 nonce 不重复 + AAD 绑定序号守住前提。

### Q16：为什么选 X25519 这条曲线？不用国密 SM2 / NIST 曲线？
**先说人话：** 不是 X25519"最好"，而是整套协议规范、论文和字节格式都长在 Curve25519 上——换曲线等于换掉整个协议的地基，超出课程范围。国密是部署合规问题，不是这个教学项目的目标。
**标准回答：** 题目与协议生态决定：X3DH、双棘轮的整套规范和我们依据的论文都建立在 Curve25519 上，X25519 有 RFC 7748 的字节格式、实现成熟（Bernstein 2006 的速度与抗侧信道设计）。换曲线等于换掉整套协议的字节级定义，超出课程范围。若老师问国密合规：那是部署合规问题，不是这个协议教学项目的目标，我们会在结论里区分「教学实现」与「生产合规」。
**可能追问：** 问"NIST 曲线差在哪"：不是差，是生态不同——P-256 在 TLS/证书体系里是主流，但 Signal 系协议全部用 Curve25519，互操作与文献都以此为准。问"SM2 能做同样的事吗"：数学上可以（也是 ECDH + 签名），但要重写整套字节级协议定义并自担分析责任，不在本项目范围。

## 四、实现类

### Q17：密码运算是自己写的吗？用了什么库？
**先说人话：** 密码原语全部用成熟库——自己写曲线运算是安全大忌，就像自己造刹车片。我们写的是"协议编排"：让这些原语按 X3DH、双棘轮的规矩配合起来。
**标准回答：** 全部调用 Python `cryptography` 库（曲线、AES-GCM、HMAC、HKDF、Ed25519；ML-KEM 需要 44.0 以上版本）。仓库里没有自研曲线公式——密码原语自己写是安全大忌，我们只实现协议编排：x3dh.py、double_ratchet.py、prekeys.py 三个文件，且不许导入网络与数据库，纯字节进出、可离线单测。
**可能追问：** 问"怎么保证编排没写错"：性质测试 + 攻击演示 + 跨实现互操作三层（Q22）。问"为什么协议模块不许碰网络"：把密码逻辑和 IO 彻底分开，单测能离线复现每一次握手和棘轮步，出了问题能定位到字节级。

### Q18：私钥在本地怎么存？口令忘了怎么办？
**先说人话：** 私钥住在"保险库"里：口令慢火熬 60 万次成钥，再用这把钥把整个保险库加密。忘了口令就是打不开——这不是 bug，是端到端设计的固有代价：服务器没有口令，帮不了你，Signal 也一样。
**标准回答：** 口令经 PBKDF2-HMAC-SHA256 做 600,000 次迭代、16 字节随机盐，派生 32 字节钥，再用 AES-256-GCM 封存身份私钥、未用完的 OPK/PQOPK 私钥和全部棘轮状态。服务器不保存口令，所以口令忘了就是解不开本地保险库——这是端到端设计的固有代价，和 Signal 的本地库逻辑一致；v2 的备份设计也是围绕这个约束做的（加密备份包、丢了就是丢了，明说）。
**可能追问：** 问"60 万次迭代的依据"：对齐 OWASP 对 PBKDF2-HMAC-SHA256 的现行推荐量级——让离线猜口令的成本足够高，同时正常登录只慢不到一秒。问"盐为什么随机且每人不同"：防彩虹表和批量预计算；两人口令相同，熬出的钥也不同。问"保险库文件被偷走呢"：偷走的是密文，仍要过 PBKDF2 + GCM 两关；口令强度就是最后一道防线，所以引导用户设长口令。

### Q19：群上限为什么是 8 人？性能瓶颈在哪？
**先说人话：** 逐人信封的安全是拿"线性成本"买的：群里多一个人，每条消息就多封一封。8 人时每条发 7 封，还很轻松；到 100 人就是 99 封，谁都受不了——所以小群用信封、大群才该上 Sender Keys/MLS，这是分工不是缺陷。
**标准回答：** 逐人信封的发送成本是 O(n)：一条群消息要对每个其他成员各跑一遍双棘轮、各发一封。8 人时是 7 封，延迟和带宽都可接受；再大就线性恶化。生产级大群应该用 Sender Keys 或 MLS，但那正是我们为了保留逐对前向安全而放弃的——这是有意识的取舍，不是没做到。文件在群里只上传一份密文、钥匙逐人分发，所以大文件不随人数放大。
**可能追问：** 问"瓶颈到底在哪一步"：发送方的加密与上传是 n−1 份小信封，瓶颈是消息数而不是单条计算——棘轮每封只是几次 HMAC + 一次 GCM（Q29）。问"8 这个数字怎么定的"：课程演示规模内保证延迟无感的最大常用群规模，且在 README 与报告中明示为设计上限，不是测出来的崩溃点。

### Q20：服务器到底能看到什么？请列全。
**先说人话：** 这题要"列全"，而且要把能看和不能看分开说——尤其别藏元数据。老师最反感的是只报喜不报忧。
**标准回答：** 能看到：用户名、双方身份公钥与预密钥池（公钥本来就公开）、谁在给谁发信封、信封大小与时间、离线队列；社交功能（好友关系、朋友圈、入群邀请与申请）是明文存服务器的。看不到：口令、私钥、SK/RK/CK/MK、消息正文、文件字节与文件名、语音内容。我们没有做密封发送者，所以「谁和谁通信」这个社交图是可见的——已知缺口，后续计划里有。
**可能追问：** 问"服务器被黑了会怎样"：见 Q31，泄露面就是上面"能看到"那一列，正文与私钥不在服务器上。问"信封大小能泄露什么"：能猜消息类型（文本/文件/语音）和大致长度，这是元数据保护要解决的问题，我们没做、明说。答辩时可直接翻 PPT 架构图页的红绿对照条。

### Q21：指纹核对如果用户就是不做呢？第一次注册被换钥怎么办？
**先说人话：** 这是全场最该诚实的一题：不核对指纹，中间人就挡不住——所有 E2EE 都一样。我们能做的是把"能被换"的窗口压到最小，但压不到零；第一次注册就被换，是无解的，明说。
**标准回答：** 不核对，就回到 Q 答的中间人情形——这是所有无中心目录 E2EE 的共同软肋（Signal 同样靠安全码核对）。我们能做的是降低被换的窗口：客户端第一次见到对方身份公钥就钉住，之后 bundle 里身份公钥变化直接拒绝并告警，所以攻击窗口只剩「第一次接触之前」。但第一次注册时服务器就换钥，挑战应答也只能证明「你拿着服务器当初收下的那把私钥」——这点我们在 README 和报告里都明说了，不假装解决。
**可能追问：** 问"那这套东西还有什么用"：把信任从"永远相信服务器"降到"只需第一次线下核对一次"，且核对后服务器再换钥立刻暴露——攻击成本与被发现概率完全不同。问"能不能用证书/CA 解决"：那是把信任转给 CA，是另一套信任模型（TLS 走的就是这条路）；Signal 系选择的是去中心 + 用户核对，我们沿用并讲清代价。

### Q22：95 个测试都测了什么？怎么证明实现是对的而不是自洽？
**先说人话：** "自洽"是指自己测自己、永远全对。我们的反驳有三层：性质测试查"该成立的数学性质成不成立"，攻击演示查"坏人来了挡不挡得住"，互操作查"别人独立写的实现能不能和我们对上字节"——第三层最有说服力。
**标准回答：** 三层。一是协议性质测试：双方 SK 字节级一致（有/无 OPK 两条路径）、往返消息明文一致、回复后棘轮代数加一、乱序可解、重放被拒、改一字节 GCM 失败且不污染后续消息、跳过超 40 拒绝。二是攻击演示：demo_attack（掉包中间人）、demo_group_attack（伪造群名单四种情形）、demo_paper_binding（论文—代码对应）。三是跨实现互操作：v2 的 JS 实现与真实 v1 引擎完成后量子互操作 12/12——两个独立实现字节级互通，是对「自洽」最有力的反驳。
**可能追问：** 问"95 个里 GUI 的呢"：95 是用例总数，其中 GUI 用例需要桌面 Qt 环境；无头环境能跑的是协议与逻辑层用例——报数字时按这个口径，别说"95/95 全过"。问"互操作具体测什么"：JS 端生成的握手材料 Python 端能解、反之亦然，含后量子封装路径，共 12 项。

### Q23：附件 8GiB 怎么做到的？为什么不直接塞进棘轮消息？
**先说人话：** 聊天信封是"小卡车"，装不下家具；文件走"货运专线"：整份文件一把钥、分片加密、流式传输，只有那把文件钥坐进棘轮信封这辆"小卡车"里送过去。
**标准回答：** 聊天信封有 64KB 上限，文件本体走第二层：一把随机 32 字节文件钥，按 8MiB 分片做 AES-256-GCM，边读边加密边发（二进制帧，不再 base64），整文件 SHA-256 和文件钥只放在棘轮信封的内层 JSON 里。接收方先验棘轮信封、再逐块验 GCM、最后核对整文件摘要，任一步失败整份丢弃、不留半截文件。8GiB 是发送前按文件大小的前置拒绝上限。
**可能追问：** 问"分片 nonce 怎么不重复"：Q5 已答——8 字节随机前缀 + 4 字节块序号，AAD 绑文件编号、块序号、总块数，块对调也会被发现。问"传一半断网呢"：任一步失败整份丢弃，不留半截文件——完整性优先于断点续传，续传不在本期范围。

### Q24：语音通话的密钥从哪来？为什么不走棘轮逐帧加密？
**先说人话：** 通话钥不另起炉灶：它搭邀请信令的"顺风车"，用现成的棘轮信封送过去，安全性直接继承会话。接通后每帧用这把钥加密——因为通话是双向实时流，棘轮那种"你一句我一句"的换链节奏跟不上 40 毫秒一帧。
**标准回答：** 通话钥放在邀请那一封棘轮信封的内层 JSON 里（invite/accept 等信令本身也是棘轮信封），所以信令与钥分发继承会话的全部安全性质。接通后每 40ms 一帧用通话钥做 AES-256-GCM（帧魔数 ECC1，nonce 首字节区分主叫/被叫防序号撞车）。逐帧推进棘轮不现实：通话是双向实时流，棘轮的请求—响应式换链对不上帧节奏，且丢一帧就会卡住整条链——这是用会话内子钥的标准折中，报告里有说明。
**可能追问：** 问"通话钥一把用全程，前向安全呢"：通话钥随信令走棘轮，会话层面的前向安全在；单通通话内不逐帧换钥是实时性的折中，报告明示。问"录音文件呢"：语音消息走的也是第二层加密（同文件路径），和实时通话是两条链路，别混。

## 五、新增高频问题（v2 补充）

### Q25：为什么不直接用现成的 Signal / libsignal？自己实现图什么？
**先说人话：** 这是课程项目——课程要考的就是"你能不能把协议实现出来"，直接调库等于把作业外包。而且我们的两个核心创新（棘轮层后量子、逐人信封群聊）在 libsignal 里根本不存在，调库反而做不出来。
**标准回答：** 三个理由。一是课程目标：题目要求实现 ECDH 协商与 AES-GCM 加密的完整链路，用 libsignal 等于把核心部分变成黑盒，学不到也考不出。二是设计空间：PQ 混合棘轮（pq-dr-v1）和逐人信封 + 签名哈希链都不是 Signal 现行部署的一部分，基于 libsignal 无法实现这两点。三是可验证性：自己实现才能做到协议模块纯字节进出、95 个性质测试逐条对应论文结论、再用 v2 的独立 JS 实现做互操作反证。当然，生产产品应该用经过审计的库——这是教学实现与生产选型的区别，我们会在结论里区分。
**可能追问：** 问"那 TLS 呢，现成的为什么不用"：TLS 保护的是"客户端到服务器这一跳"，服务器仍能看明文——它解决的是传输安全，不是端到端；两者保护对象不同（Q26）。问"自己实现不怕写错吗"：原语全部用成熟库（Q17），自己写的只有编排层，且有三层验证兜底（Q22）。

### Q26：和微信 / QQ 的加密有什么区别？
**先说人话：** 一句话：微信是"信在邮局要拆开检查再封上"，我们是"信封在你手里就封死，邮局只负责送"。技术说法：它们是传输层加密，服务器持有解密能力；我们是端到端，服务器没有钥匙。
**标准回答：** 主流国产 IM 用的是传输层加密（TLS 类）：消息在你的设备到服务器之间是加密的，但服务器解密、处理、再加密转发——运营商在技术上能看到明文，安全依赖"相信运营商 + 内部管理"。ECNUchat 是端到端加密：加密在发送方设备完成、解密只在接收方设备，服务器全程只有密文（Q20 的清单就是证据）。代价也要讲：E2EE 让服务器帮不了你找口令、做不了内容审核、多设备同步更难（Q18、Q30）——这是模型差异，不是简单的"谁更先进"。
**可能追问：** 问"微信也有'加密'宣传，为什么不一样"：看钥匙在谁手里——传输加密的钥匙终点是服务器，端到端的钥匙终点是对方设备；判断标准就这一条。问"国家监管怎么看 E2EE"：这是部署与合规层面的问题（与 Q16 的国密问题同类），本项目是教学实现，不在讨论范围，但可以在结论里主动区分。

### Q27：量子计算机真有那么可怕吗？是不是炒作？
**先说人话：** 不用渲染"量子末日"。真正的威胁不是"明天量子计算机就造出来"，而是"先存后解"：有长期保密价值的密文，今天被存下来，十年后解开也是泄露。所以后量子是给"需要保密很多年"的数据上的保险，现在就得上。
**标准回答：** 分两层说。第一，Shor 算法在数学上确实能破 X25519 这类基于离散对数的体系，这不是争议点；争议只在"足够大的容错量子计算机什么时候出现"，时间线从十年到更久都有估计。第二，无论时间线如何，"先存后解"（harvest now, decrypt later）使风险前置：对手今天就可以低成本囤积密文。所以 NIST 2024 年把 ML-KEM 标准化、各大协议（Signal PQXDH、TLS 混合密钥交换）都在迁移——业界共识是"迁移要趁早"，我们的项目跟随的正是这个共识，而不是炒作时间线。
**可能追问：** 问"ML-KEM 就一定安全吗"：它是基于格难题（Module-LWE）的，不同于离散对数，目前没有已知的量子算法能高效解；且我们是混合构造，ML-KEM 万一出问题还有 X25519 兜底（Q7）。问"AES 会被量子破吗"：Grover 算法只相当于把 AES-256 的有效强度降到约 128 位，仍然安全——这正是选 256 位的原因之一。

### Q28：ML-KEM 为什么选 768？不用 512 或 1024？
**先说人话：** 768 是"中间档"：512 余量偏薄，1024 更保守但钥匙和密文更大、算得更慢。768 对标 NIST 第 3 级安全，也是 Signal 的 PQXDH 选的同一档——有部署先例背书。
**标准回答：** ML-KEM 三档对应 NIST 安全等级 1 / 3 / 5。768（第 3 级，大致对标 AES-192 的攻击成本）在安全余量与体积、速度之间最均衡：它的封装钥和密文比 1024 小一截，而我们的场景里 PQOPK 要成池存放、棘轮每条新链都要做一次封装，体积与频率都敏感。更重要的是生态一致：Signal 的 PQXDH 用的就是 Kyber768 / ML-KEM-768 这一档，我们的构造对齐（Q11）也包括参数对齐。
**可能追问：** 问"768 的密文多大"：ML-KEM-768 封装密文约 1088 字节、公钥约 1184 字节，比 X25519 的 32 字节大得多——这正是它只在握手和换链时用、不用在每条消息上的原因之一。问"以后能升级到 1024 吗"：标签带版本号（pqxdh-v1）就是为参数与算法升级留的域分离空间（Q14）。

### Q29：这一套加密的性能开销有多大？用户能感觉到吗？
**先说人话：** 分三笔账：每条消息的账很小（几次哈希 + 一次对称加密），握手的账中等但只付一次，群聊的账随人数线性涨——真正的瓶颈从来不是密码运算，是群信封的数量。
**标准回答：** 诚实口径：我们没有做正式的基准测试报告，所以不报具体毫秒数，只报量级与结构。每条消息：对称棘轮是两次 HMAC + 一次 AES-GCM，都是对称运算，桌面端完全无感。每次握手：四次 X25519 + 一次 ML-KEM 封装，是一次性成本。每次换链：一次 DH + 一次 KEM 封装。真正随规模恶化的是群聊的 O(n) 信封（Q19）。如果老师要求数据，现场可以跑 pytest 的协议用例计时，或者把基准测试列入后续计划——不要现场编数字。
**可能追问：** 问"Python 会不会太慢"：见 Q33——热点全在 `cryptography` 库的 C 实现里，Python 只做编排。问"手机上呢"：本期是桌面/终端双端，移动端不在范围；协议本身在 Signal 的移动端部署已证明可行。

### Q30：Bob 换了新手机 / 新设备，会发生什么？
**先说人话：** 新设备 = 新身份：会生成全套新钥匙，指纹会变，老对话的钥匙不在新设备上。所以换设备在我们这里是"重新开始"，不是"同步过去"——单设备是本期的明确范围，多设备是已知缺口。
**标准回答：** 当前是单设备设计：新设备注册会生成新的 IK_sign / IK_dh 等全套钥匙，对方客户端会看到身份公钥变化并告警，需要重新线下核对指纹（这正是钉住机制在起作用）。历史消息不会迁移，因为旧棘轮状态只在旧设备的保险库里。Signal 的多设备（每台设备独立身份 + 链接机制）是独立的大工程，我们列在已知缺口里，没有假装支持。
**可能追问：** 问"旧设备丢了怎么办"：等同于口令遗忘 + 设备丢失的组合（Q18）：保险库在旧设备上，新设备重新注册、重新核对指纹；服务器上只有密文信封，找不回历史。问"能不能做加密备份恢复"：v2 的备份设计就是加密备份包（Q18），恢复仍需用户自己的口令，服务器不参与。

### Q31：服务器被黑客攻破、数据库被拖走，历史消息会泄露吗？
**先说人话：** 不会泄露正文。服务器上压根没有明文，也没有任何人的私钥——黑客拖走的是一大堆"没有钥匙就打不开的信封"，还有一堆本来就公开的公钥。真正会泄露的是外围信息：谁和谁在聊、好友关系、朋友圈这些明文存的东西。
**标准回答：** 泄露面就是 Q20 清单里"服务器能看到"的那一列：公钥与预密钥池、信封密文、社交图与时间大小等元数据、明文社交数据。正文泄露不了：SK、MK 从来没到过服务器，每条消息的 MK 在客户端用完即删；信封密文没有任一方的私钥就是随机数。另外服务器不存口令（登录是挑战应答），所以也没有"撞库"问题。
**可能追问：** 问"黑客拿着密文等量子计算机呢"：这正是先存后解场景——握手与新链都有 ML-KEM 兜底（Q27），历史会话的后量子部分不是靠 X25519 单独保护的。问"内鬼呢"：内鬼能做的上限就是 Q20 的可见清单加换包攻击，换包靠指纹核对挡（Q21）。

### Q32：群里有人退群 / 被踢，他还能看到新消息吗？新加入的人能看历史吗？
**先说人话：** 都不能，原因特别朴素：没人给他封信封，他就没有钥匙。但要主动交代一个边界：我们那条"管名单的链"目前只认"加人"，不认"删人"——删人这个动作还没做进链的规则里，别吹成已实现。
**标准回答：** 分三层。第一，密码学层面：成员不在名单后，后续群消息不再逐人给他封信封，他拿不到新消息的 MK，自然解不开；新成员同理看不到入群之前的历史，因为那些信封从没封给过他。第二，实现边界：当前签名哈希链的状态迁移规则只有"每纪元只增一人"，删除成员未纳入链规则——演示里连合法签名发起的删人都会被拒，所以"踢人"目前不是完整实现的功能，列入已知边界。第三，退群者已合法收到的旧消息他当然还能看——已经看到的内容密码学管不了，任何 IM 都一样。
**可能追问：** 问"那群管理岂不是残缺"：诚实认：中期阶段优先保证了"名单不可伪造"这条安全底线（加人必须签名、链可验），删人迁移是后续计划里明确的一项。问"为什么加人要搞这么严"：因为加错一个人 = 正文多泄露一份，Q13 的幽灵成员就是这个风险。

### Q33：为什么用 Python 写？性能和安全合适吗？
**先说人话：** 真正干重活的加密运算全是 C 语言写的库在跑，Python 只负责"指挥调度"，就像包工头不亲自搬砖。课程项目最重要的是把协议讲清楚、测明白，Python 最合适。
**标准回答：** 三点。一，原语层：曲线、AES-GCM、HMAC、HKDF、ML-KEM 全部来自 `cryptography` 库的底层实现（C/OpenSSL 系），热点不在 Python 解释器里。二，编排层：握手与棘轮是字节处理加状态机，Python 表达清晰、可测性强，95 个用例可离线复现每一歩。三，瓶颈不在语言：系统真正的成本是群聊 O(n) 信封数量（Q19、Q29）。诚实边界：生产级客户端会用 Rust/C 写热路径（Signal 客户端就是），本项目是教学实现，选型逻辑不同。
**可能追问：** 问"Python 的动态类型会不会埋安全坑"：协议模块纯字节进出、接口收窄，再用性质测试兜底（Q22）；且密码模块禁止导入网络与数据库，出问题可定位到字节级（Q17）。

### Q34：老师指着某个功能问"这段代码在哪"，怎么答？
**先说人话：** 别慌，记住三个核心文件 + 三个演示脚本就够了，剩下的现场打开仓库搜函数名，天经地义。

### Q35：两万行代码、95 个测试，怎么证明是真做出来的、不是套壳？
**先说人话：** 三个硬证据，背下来：① 仓库提交历史是连续的，时间线造不了假；② 两个独立实现能字节级互通，套壳套不出这个；③ 攻击演示现场就能跑，挡不挡得住当场见分晓。
**标准回答：** 一，GitHub 仓库公开，提交历史完整可查。二，互操作：v2 的 JS 实现是独立重写的，与 v1 Python 引擎完成后量子互操作 12/12——如果只是套壳或自说自话，不可能与独立实现字节级对齐。三，现场性：三个攻击演示和全套测试在答辩现场可直接运行，结果即时可见。四，规模口径要诚实：源码约两万行含 v1+v2 与测试；95 是用例总数，GUI 用例需要桌面 Qt 环境（Q22 的口径）。

### Q36：同一个人能不能在两台设备同时登录？（多设备）
**先说人话：** 不能。一台设备就是一个身份，这是我们明说的范围，不是偷偷缺的。
**标准回答：** 当前是单设备设计（Q30）：第二台设备注册会生成全新身份钥、指纹不同，对方端会告警并要求重新核对。多设备在 Signal 里是独立的一套机制——每台设备独立身份，再用主设备签发"设备链接"把它们绑成一个人——工程量与一台主协议相当，我们列入已知缺口与后续计划。本期把单设备的协议正确性、后量子与群方案做扎实，优先于铺多设备。
**可能追问：** 问"用户体验岂不是很差"：是取舍：目标用户与课程范围下，先保证单设备的安全性质全部成立；且 v2 已在做浏览器端与中继，多设备是路线图上的明确下一项，不是回避。
